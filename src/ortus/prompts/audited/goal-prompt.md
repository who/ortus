Read `AGENTS.md` first. A goal window covers one issue, from the id it opens with to the session-close that ends it. The next issue arrives in a fresh process, so one issue per window and no compaction is the shape of a correct run.

1. **Orient.** A ninety-second standup: what is in flight, what just happened, what the tree looks like. Work specs open in step 2. Each `bd` invocation is its own Bash call with `bd` as the first token, and each git invocation is its own call too.
   - `bd list --status=in_progress --json --brief` — leftover claims, each with its labels.
   - `bd events tail --limit 20 --json` — recent closes, comments, claims, creates. Comments (`op=comment`) are the interesting lines, closes next. `bd events` starts at enable and does not backfill older comments.
   - `git log -5 --oneline` — what actually landed.
   - `git status --porcelain` — inherited dirty paths.
   A standup at this altitude reads lists. The packet reads belong to step 2, where `bd show <id> --json` is the work spec and `bd comments <id> --json` is that ticket's thread.

2. **Continue or select.** When a Bound issue contract v1 is injected, its JSON issue id is opaque data. Read only that id with bd show, quoting it as one argument after --. Verify it is still in_progress, has no human label, and its assignee matches BEADS_ACTOR. On mismatch or multiple non-human in_progress issues, record PLAN-GAP, flag human and stop without selecting another issue. Otherwise continue only the bound id, skip bd ready and claiming, and retain the normal implementation and session-close steps. Without that injection, use the selection rules below. An `in_progress` issue labeled `human` is the operator's repair queue, so a window whose every `in_progress` id carries that label is a window with nothing in progress. Exactly one `in_progress` issue without the label is the id this window continues. Two or more of them is an ambiguous queue: flag human, comment PLAN-GAP, and stop there. With nothing to continue, `bd ready --json` lists the candidates — an empty list ends the window with no sentinel, an id labeled `human` is awaiting operator repair rather than work, and the first remaining non-epic id is the claim, taken with `bd update <id> --status=in_progress`. Its `bd show <id> --json` packet is the work spec.

3. **Investigate and implement** that one issue. CodeGraph is the orientation surface wherever the injected CodeGraph contract names it. Verification is whatever the composed instruction names: the issue's criterion-check commands, or the lint and syntax gate of an injected `## Prototype verification` section in place of those commands, with `docs/testing.md` as further guidance only if that file exists. A failing check is unfinished work, so it gets fixed here. Every check this window starts also finishes here — a check still running when the turn ends has produced no result, and a criterion check that cannot finish inside one window is a defect in the work spec rather than a long wait: it stays unstarted, with a PLAN-GAP comment, a human flag, and a stop. A version, date, or toolchain value this repository declares past what the installed tool supports is pin-able: lowering it to the value the installed tool honors, filing a follow-up bead to restore it, and continuing the claim is the correct end state. Credential gaps, uninstalled tools, and unmade product decisions stay PLAN-GAP plus a human flag. Leftover work becomes new beads instead of extra scope on this id, and `bd memories <keyword>` for the subject comes before filing or re-scoping one: owner-decision memories, the keys carrying a `policy` or `decision` token, bind the new bead's Non-goals and Resolved decisions.

4. **Session-close** that id per `AGENTS.md`: completion comment, commit, `bd close`, `git pull --rebase --autostash`, `bd dolt push`, `git push`. The close and the push are this window's work rather than an outer process's.

5. **Exit.** No sentinel. The goal is reached when that issue is closed and HEAD is in sync with origin. The checks from step 3 are the whole verification, so pytest and the repo suite stay unrun after them. The answer is the id, the close reason, the HEAD sha, and those commands — written once everything this window started has finished, with the implementation left unread and no second issue begun.
